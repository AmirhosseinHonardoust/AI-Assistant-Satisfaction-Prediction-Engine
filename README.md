## Project Overview

Predicting user satisfaction is not only a classification problem. To be useful, a model score has to support a defensible interpretation:

- predict a 1-5 satisfaction rating from session behavior
- measure how *close* predictions are, not just whether they are exact
- report calibrated confidence, not raw scores
- explain which behavioral features drive each decision
- state clearly what the data can and cannot support

This project demonstrates that end-to-end workflow on a synthetic daily-usage dataset. It generates data from a documented latent process, engineers time features, trains a scikit-learn pipeline, evaluates it with ordinal-aware and calibration metrics, explains it with SHAP, and exposes everything through a Streamlit dashboard.

The goal is to show how a satisfaction model becomes an **interpretable decision-support workflow** whose modest results are honest and reproducible, rather than a single inflated accuracy number.

---

## What This Project Does

This project can:

- Generate a synthetic daily-usage dataset from a documented latent process
- Engineer time features (`hour_of_day`, `day_of_week`, `is_weekend`) from timestamps
- Train a calibrated multi-class satisfaction model using a scikit-learn pipeline
- Evaluate accuracy, cross-validated accuracy, MAE, quadratic-weighted kappa, log loss, and ECE
- Compare the model against a majority-class baseline
- Compare flat multi-class against a Frank & Hall ordinal model reproducibly
- Produce a reliability diagram and calibration diagnostics
- Explain global drivers and per-session predictions with SHAP
- Score new session CSVs with predicted rating and per-class probabilities
- Provide a Streamlit dashboard for exploration and per-session explanations
- Run automated tests and a GitHub Actions quality gate plus pipeline smoke workflow

---

## What This Project Does Not Do

This project does **not**:

- Measure real users' satisfaction with any real AI assistant
- Provide product, UX, or business recommendations
- Use a production or real-world dataset
- Guarantee that the designed effects match human behavior
- Provide real-time inference infrastructure
- Include monitoring, drift detection, or retraining automation
- Certify the model for any high-stakes or customer-facing decision

A real analytics system would need genuine user data, privacy and consent controls, monitoring, experiment design, and domain review.

## Key Features

- **Documented synthetic generator** so the "ground truth" behavioral signal is explicit and reproducible
- **Multi-class satisfaction model** (RandomForest inside a preprocessing pipeline)
- **Ordinal-aware evaluation** with mean absolute error and quadratic-weighted kappa
- **Honest baselining** against a majority-class classifier
- **Cross-validated accuracy** reported next to the single-split number
- **Frank & Hall ordinal comparison** kept as a reproducible experiment, not an assertion
- **Calibration diagnostics** with a reliability diagram and Expected Calibration Error
- **SHAP explainability** for both global drivers and per-session contributions
- **Version-robust SHAP handling** across the list and ndarray output conventions
- **Streamlit dashboard** for distribution, segmentation, and per-session explanations
- **Unit tests and GitHub Actions CI** with a full-pipeline job that publishes artifacts
- **Model as a build artifact** (trained by CI and locally, not committed to git)

## Quick Start

The whole workflow runs with zero external data — the raw dataset is generated
from a documented process:

```bash
python -m src.generate_data     # create the synthetic raw dataset
python -m src.data_prep         # time features + stratified train/test split
python -m src.train_model       # train, evaluate, write model + metrics
```

Generate figures and explanations, then launch the dashboard:

```bash
python -m src.evaluate          # confusion matrix, per-class F1, reliability, ordinal comparison
python -m src.explain           # global SHAP summary
streamlit run app.py
```

Everything is deterministic given the fixed `RANDOM_STATE` (42).

## Ordinal vs Flat Comparison

The 1-5 target is ordered, so a natural question is whether a dedicated **ordinal**
model beats flat multi-class. This is tested reproducibly in
`src/evaluate.py` (`compare_ordinal_vs_flat`), which fits a Frank & Hall ordinal
wrapper (`src/ordinal.py`) on the same split and writes
`reports/metrics/ordinal_comparison.json`.

<div align="center">

| Model | Accuracy | MAE | QWK |
|---|---|---|---|
| Flat RandomForest (default) | **0.483** | **0.713** | **0.726** |
| Frank & Hall ordinal RF | 0.397 | 1.007 | 0.640 |

</div>

The flat forest wins on every metric — it already respects the ordering, and its
quadratic-weighted kappa of **0.726** shows most errors are adjacent ratings — so
it stays the default. The ordinal model is kept as a documented, tested
alternative rather than dropped, so the conclusion is checkable, not asserted.

> This is an experiment, not a claim: swap in the ordinal model if your data behaves differently.

## Calibration and Reliability

`predict_proba` reliability is measured with a reliability diagram and Expected
Calibration Error (ECE), which compares predicted confidence against observed
accuracy.

The RandomForest is moderately calibrated (**ECE ≈ 0.091**). Post-hoc sigmoid
(Platt) recalibration reduces ECE to about 0.06 but costs roughly 3 points of
accuracy, so it is reported rather than applied by default. Enable it downstream
with `sklearn.calibration.CalibratedClassifierCV` if trustworthy probabilities
matter more than exact-rating accuracy for your use case.

> Calibration diagnostics describe probability quality; they are not a guarantee of correctness.

## Evaluation Metrics

The evaluation layer reports metrics designed for an ordered, noisy target.

<div align="center">

| Metric | Why it matters |
|---|---|
| Accuracy | Exact-rating hit rate at the default decision rule |
| 5-fold CV accuracy | Stability across folds, so the split is not cherry-picked |
| Majority baseline | Chance reference for a balanced 5-class target |
| Quadratic-weighted kappa | Agreement that rewards near predictions (ordinal quality) |
| Mean absolute error | Average rating distance — most misses are off-by-one |
| Log loss | Probability quality across all classes |
| ECE | Calibration gap between predicted confidence and accuracy |

</div>

Example results from the included run:

<div align="center">

| Metric | Example value |
|---|---|
| Accuracy | 0.483 |
| 5-fold CV accuracy | 0.429 ± 0.036 |
| Majority baseline | 0.200 |
| Lift over baseline | +0.283 |
| Quadratic-weighted kappa | 0.726 |
| Mean absolute error | 0.713 |
| Log loss | 1.251 |
| Expected calibration error | 0.091 |

</div>

> These values come from a synthetic dataset and demonstrate the workflow; they are not real-world satisfaction measurements.

## Testing and CI

Run unit tests locally:

```bash
python -m pytest
```

Run the quality gate locally (matches CI):

```bash
ruff check .          # lint (E, F, I, B, SIM, UP), line-length 100
black --check .       # formatting, line-length 100
mypy src app.py       # static type checking
pytest                # 20 unit tests (heavy shap/streamlit tests skip cleanly)
```

The GitHub Actions workflow runs two jobs:

- **quality-gate** — ruff, black, mypy, and pytest on Python 3.10 and 3.12
- **pipeline** — runs `generate_data → data_prep → train_model → evaluate → explain` end-to-end and uploads the trained model and reports as artifacts

This exercises the full training path in CI, not just the unit tests. CI is
defined in:

```text
.github/workflows/ci.yml
```

The 20 tests cover time-feature engineering, the training pipeline, the
stratified split, batch scoring round-trips, the documented data signal, the
version-robust SHAP shape helpers, the Frank & Hall ordinal classifier, and the
ordinal/calibration metric helpers (ECE, MAE, QWK).

## Limitations

This project has important limitations:

- The dataset is synthetic, not real user data
- Results reflect a *designed* signal, not real human behavior
- Metrics do not prove real-world satisfaction-prediction performance
- Moderate accuracy (~0.48, CV ~0.43) is intentional to keep the task realistic
- A Frank & Hall ordinal model was evaluated and did not beat the flat forest here
- No per-user personalization or temporal modeling is included
- The dashboard is a demo, not a secure analytics platform

The project is strongest as a portfolio demonstration of an honest, reproducible
ML workflow with explainability and calibrated evaluation.
