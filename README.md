---

## **Overview**

This project implements an end-to-end machine learning pipeline for predicting **user satisfaction** with an AI assistant from recorded session behavior. It mirrors the analytics workflows used to study user experience: ingest behavioral data, engineer features, train and evaluate a model, explain its decisions with SHAP, and expose everything through an interactive dashboard.

The dataset is **synthetic and generated by a documented process** (see [`src/generate_data.py`](src/generate_data.py)). Satisfaction is drawn from a known latent scoring function of device, usage category, model, session length and weekend effect, plus Gaussian noise. Because the data-generating process (DGP) is explicit, the "behavioral insights" below are **verifiable**: a good model should recover the effect sizes that were designed in — and it does.

The pipeline performs:

* **Feature engineering** from timestamps
* **Behavioral signal extraction** (device, usage category, model used)
* **Supervised multi-class prediction** (satisfaction rating 1–5)
* **Model explainability** using SHAP
* **Evaluation** with an honest majority-class baseline
* **Interactive analytics dashboard** built in Streamlit

---

## **Results (measured)**

Trained on 1,200 sessions, evaluated on a held-out 300-session test set:

| Metric | Value |
| ------ | ----- |
| Test accuracy | **0.483** |
| Majority-class baseline | 0.200 |
| Lift over baseline | **+0.283** |
| Macro F1 | ~0.47 |

Chance for a balanced 5-class problem is 0.20, so the model reaches roughly **2.4×** the baseline. This is a deliberately honest, moderate result: satisfaction is noisy by construction, and adjacent ratings are genuinely hard to separate — which is what a real ordinal satisfaction signal looks like. Metrics are written to [`reports/metrics/metrics.json`](reports/metrics/metrics.json) on every training run.

# **Dataset Description**

The generated dataset contains **1,500 interaction sessions** with these core features:

| Feature                  | Meaning                                       |
| ------------------------ | --------------------------------------------- |
| `timestamp`              | When the session occurred                     |
| `device`                 | Desktop, Mobile, Tablet, Smart Speaker        |
| `usage_category`         | Coding, Productivity, Research, Writing, etc. |
| `prompt_length`          | User prompt length                            |
| `session_length_minutes` | Engagement duration                           |
| `satisfaction_rating`    | Target label (1–5)                            |
| `assistant_model`        | GPT-4o, GPT-5, GPT-5.1, Mini, o1              |
| `tokens_used`            | Tokens used by AI response                    |

## **Engineered Time Features**

From `timestamp`, the pipeline derives `hour_of_day`, `day_of_week` (0 = Monday) and `is_weekend`. The generator gives weekend sessions a small positive satisfaction bump, so this feature carries real (if modest) signal.

---

# **ML Pipeline Architecture**

* **ColumnTransformer** for preprocessing
* **OneHotEncoder** for categorical features
* **StandardScaler** for numerical features
* **RandomForestClassifier** with class balancing
* **SHAP** explainability layer
* Evaluation scripts and an honest baseline

| `device_Smart Speaker`   | Positive (+1.1)                 |

This is the key point: because the DGP is documented, the explanation is **checkable**, not a just-so story. The model recovers what was built in.

---

# **Behavioral Insights (by construction)**

These patterns are *designed into the synthetic data* and *recovered by the model*:

1. **Device shapes experience** — Smart Speaker and Desktop rate highest; Mobile lowest.
2. **Task type matters** — Coding and Research skew positive; Entertainment and Daily Tasks skew lower.
3. **Model capability matters** — GPT-5.1 > GPT-5 > GPT-4o > o1 > Mini.
4. **Weekend bump** — weekend sessions get a small positive offset.
5. **Engagement** — longer sessions trend slightly more positive.

> In a real deployment these would be hypotheses to validate; here they are ground truth that the pipeline demonstrably learns.

# **Reproducibility**

Everything is deterministic given the fixed `RANDOM_STATE` (42).

```bash
pip install -r requirements.txt

python -m src.generate_data   # 1) create the synthetic raw dataset
python -m src.data_prep       # 2) time features + stratified train/test split
python -m src.train_model     # 3) train, evaluate, save model + metrics
python -m src.evaluate        # 4) confusion matrix, distribution, per-class F1
python -m src.explain         # 5) SHAP global summary
streamlit run app.py          # 6) launch the dashboard
```

# **Limitations**

* Synthetic data: results reflect a *designed* signal, not real users. Real satisfaction would be noisier and confounded.
* Moderate accuracy (~0.48) is intentional — the noise term keeps the task realistic.
* Treated as flat multi-class rather than ordinal.
* No per-user personalization or temporal modeling.

---
